# C# 图标台球实施方案

状态：2026-11-12 按用户确认完成首版 C# 实现与隔离验收，候选版本 0.13.0。实施结果、实测指标与边界见[实现与验收](图标台球实现与验收.md)，正式发布和本机应用状态以[项目交接](项目交接.md)为准。未运行上游 Python 游戏或改动真实桌面。

## 1. 确定的技术方向

使用现有 .NET 10 + WPF，保留轻匣单文件发布及共享桌面运行时依赖。移植上游球体、碰撞、摩擦、球袋和瞄准预测；画面及输入用 C# / WPF 重写，不携带 Python、Tk、Pillow 或 PyInstaller。

同一 DesktopNook.exe 增加内部游戏启动模式：日常仍只有原主进程；用户开始游戏时临时启动游戏进程，退出游戏后结束该进程。这样把持续绘制及图形资源留在游戏生命周期内。主进程负责会话管理和持久化，游戏进程使用只读图标快照，不初始化可写 NookStore。

首版采用独立台球窗口，占用所选显示器工作区，任务栏保留可切换的游戏窗口，支持 Alt+Tab。它不等同于原版嵌入 Explorer 的透明桌面图层。原版透明效果列为后续阶段，不能在首版悄悄混入隐藏 Explorer 或恢复桌面布局的行为。

## 2. 首版交付范围

| 项目 | 首版设计 |
| --- | --- |
| 入口 | 更多 → 桌面玩法 → 图标台球 |
| 图标来源 | 当前分类、全部收纳图标、桌面图标只读镜像 |
| 默认选择 | 当前页的分类；在“全部”页则默认全部 |
| 数量 | 15～45 个图标，另有 1 个白球 |
| 稀疏来源 | 1～14 个图标在游戏内复制补足，显示原数量和补足数量 |
| 来源为空 | 禁用开始，允许切换来源；不创建空白对局 |
| 来源超过上限 | 默认按当前来源顺序取前 45 个，开始前显示数量，可调整来源 |
| 玩法 | 鼠标瞄准、按住左键蓄力、松开击球、碰库、碰撞及入袋 |
| 辅助 | 瞄准线开关、力度条、击球数、已入袋和剩余数量、计时 |
| 白球入袋 | 不计进球；尝试安全复位，无空间时允许手动摆放 |
| 操作 | 暂停/继续、重新开始、退出；Esc 直接退出游戏 |
| 成绩 | 本地完成局记录及个人最佳，无全球排名 |
| 桌面与文件 | 只操作游戏图形，不收纳、删除、移动文件或写分类顺序 |

桌面来源只枚举当前可用图标及图像，不需要读取或修改它们的屏幕排列。系统图标按虚拟身份处理，普通文件优先用类型图标；提取失败使用品牌占位图。不会为了玩游戏把已收纳内容移回桌面。

同一来源的多个复制球共享纹理，但拥有不同 BallId，避免一次入袋误计多颗。游戏里的数量、坐标、球阵及进球状态不写回主索引。

## 3. 用户流程与画面

1. 点击入口，打开轻量设置窗，选择来源、图标数量和辅助线。仅显示本局必要选项，不预加载全量图片。
2. 点击开始，主面板正常收起，显示游戏载入状态；游戏准备成功后展示台球窗口。失败则恢复可操作入口并给出原因。
3. 白球在左、图标球阵在右，六个球袋。蓝青品牌边框配深青桌布，图标保留原图形；使用淡碰撞环表示有效半径，避免画面大小与碰撞范围不一致。
4. 首次击球开始计时，暂停时间不计入；最后一颗图标入袋结束本局，显示总时间、图标数、击球数和每颗平均耗时。
5. 重开确认当前局结束后重置；退出游戏即关闭临时游戏进程。主软件仍在任务栏，用户可以再次打开轻匣。

启动中连续点击只保留一个请求；游戏已存在时入口改为“继续台球”，唤醒已有窗口。界面不把游戏混入普通图标拖拽和排序手势。

失焦自动暂停，恢复焦点后由用户继续；最小化停止物理推进和绘制订阅。显示器、DPI 或窗口尺寸变化时先暂停并重建画面，重新开局前说明本局将重置，不在尺寸突变时继续推进错误坐标。

## 4. 模块与接入点

| 模块 | 职责与边界 |
| --- | --- |
| DesktopNook.Games.Core | 纯 C# 物理及计时状态，无 WPF、Shell、网络或文件写入依赖 |
| BilliardsScene / BallState | 球体、速度、有效半径、球袋、计分、暂停和回合状态 |
| GameIconCatalog | 分类/全部/桌面三种来源适配，生成稳定图标描述快照 |
| GameIconProvider | 仅在游戏进程提取和限额缓存图像，复用 SharpIcons 的路径取图能力 |
| BilliardsWindow / Renderer | 一个 WPF 二维场景，绘制图标、球杆、轨迹、球袋和入袋效果 |
| BilliardsController | 主进程中管理单局启动、IPC、退出、异常与持久化 |
| GameStorage | 在现有 Data 下保存游戏设置、完成成绩和必要诊断 |
| DesktopNook.Games.Tests | 无桌面副作用的物理和状态测试，另配原生集成检查 |

`MainWindow.OnMore` 增加入口；`App.OnStartup` 在常规单实例及 NookStore 初始化之前处理内部游戏模式。该分支只创建游戏窗口，不能把第二个进程当作另一个轻匣主实例。

主 EXE/程序集及主 AUMID 保持兼容，游戏窗口使用单独标题和可识别的临时任务栏入口。新物理类库随现有单文件打包，不额外发布 Python 游戏 EXE，不增加第二套更新器。

## 5. 物理与绘制

参考固定的上游提交移植规则，先以行为测试保持手感，再调整常量。物理采用固定步长推进并对高速运动细分，按单调时间累计；限制卡顿后的追赶量，避免一次阻塞后出现穿透或无限补算。计时与渲染帧率分离。

碰撞顺序包括球体推进、球袋判定、边界反弹、近邻碰撞、重叠修正、摩擦和静止判断。使用空间分桶减少无关球对检测，处理同中心、零速度、边界重叠和高速碰撞。瞄准预测使用相同半径和规则；先保证首次碰撞及反弹方向一致，不将辅助线描述成完整轨迹的绝对保证。

回合状态为：载入 → 就绪 → 蓄力 → 击球 → 滚动 → 就绪；白球入袋转复位/手动摆球，清台转结算。暂停保存其前态；关闭从任意状态统一清理。

渲染优先一个 DrawingVisual 或自绘 FrameworkElement 批量绘制，不为每个球创建分层原生窗口。滚动及入袋阶段目标 60 FPS；静止时停止物理步进，鼠标变化才更新瞄准，重绘合并到显示节奏。只有静止装饰效果确实需要时才降低刷新持续播放，不能为了计时维持空转帧循环。

首版用矢量桌布和图标，无动态壁纸模糊、截图背景或音频输入。入袋效果为靠近球袋、旋转缩小、淡出及短涟漪，结束后移除，避免累积不可见视觉对象。

## 6. 按需进程、IPC 与更新

主进程创建会话随机标识及当前用户限定的命名管道，随后以参数列表启动同一个 EXE。会话仅包含所选图标 ID、名称、图标路径/系统图标身份和游戏参数；不传送文件正文。校验父 PID、进程启动时间和随机标识，拒绝旧会话或其他用户连接。

协议至少包括 Ready、Start、Activate、Pause、RoundFinished、SettingsChanged、Close、Closed。Ready 前显示载入状态；就绪超时可取消并清理。图标顺序来自启动时快照；游戏期间主界面数据改变，不让游戏反向覆盖当前数据。

主进程是持久化单一写入方：游戏报告设置及成绩，主进程验证当前会话、轮次和数据范围，再原子保存。重复完成消息不能重复记成绩，未完成/中断局不记入最佳成绩。父进程失联则游戏结束；不为等待父进程保持孤儿窗口。

退出主软件、开始更新、切换/迁移数据或卸载维护前，先向游戏发送关闭并等待退出，然后才允许替换 EXE 或迁移 Data。不能把整局游戏长期占用普通 `_interactions` 计数而让维护入口一直超时；用专门游戏生命周期状态协调。用户确认更新前说明会结束当前对局。

关闭超时时先核验确为本程序启动的游戏进程；首版只操作图形，必要时可结束这一游戏进程，不终止 Explorer 或其他应用。成绩采用原子保存，避免中途退出损坏主收纳数据。

## 7. 文件位置与许可

所有游戏持久化位于当前实际 `Data`，不硬编码 E 盘：

```text
Data/Games/IconBilliards/
  settings.json       游戏来源偏好、数量、辅助线
  scores.json         最多保留最近 100 局及个人最佳
  logs/               有数量和大小上限的必要诊断
```

会话数据优先走 IPC；需要会话文件时放在此目录下，只含本局信息并在结束后清理，不把图标名称和路径默认写入长期日志。不建立新的 APPDATA 配置或自启动项。沿用 Data 的当前用户权限及现有加密策略。

保留上游 MIT 版权及完整许可文本，增加第三方许可入口，注明参考仓库与提交。主题使用轻匣已确定的 A2 标识及蓝青界面。首版不接入上游自动更新、设备标识、联网排名及服务地址。

## 8. 性能目标与发布门槛

以下是待原型验证的目标，不是当前已实现的结果；用与 0.12.13 相同的私有工作集口径比较。

| 指标 | 初步目标 |
| --- | --- |
| 日常不玩游戏 | 没有游戏进程、绘制循环或游戏图片预加载；主进程闲置增量 ≤5 MiB |
| 参与上限 | 45 个图标 + 白球，不无界扩展 |
| 图标原始像素缓存 | ≤8 MiB；含控件/GPU副本的进程占用另测 |
| 游戏运行 | 1080p 基准下游戏进程私有工作集目标 ≤120 MiB，合计主进程数值同时披露 |
| 帧率 | 运动阶段目标 60 FPS；基准机帧间隔 P95 ≤33 ms |
| 静止/最小化 | 无物理空转；最小化时停止游戏帧回调 |
| 退出 | 3 秒内游戏进程结束，无残留管道、位图、窗口和计时器 |
| 退出后主进程 | 15/60 秒采样回到游戏前基线 +5 MiB 范围，避免把子进程开销转移到主进程 |
| 分发 | 保持现有共享 .NET 运行时与单 EXE，初步体积预算 ≤2 MiB，最终据实披露 |

性能测试分别记录未打开游戏、运行 15/45 个图标、静止、最小化、退出、连续 30 次开启关闭及长时间闲置。统计所有所属进程的私有工作集与专用提交、CPU、句柄和帧间隔；不裁剪工作集或定时强制 GC 来达标。

功能验收包括：正面/斜碰/同中心/高速/贴库、白球入袋、克隆球独立计数、空来源和超限来源、辅助线、暂停计时、重开、退出、失焦、DPI/分辨率变化、来源文件不可访问、父子进程异常和更新维护关闭。游戏前后核对 `state.json`、`item-order.json` 及实际收纳文件不变。

保留既有核心、原生界面、拖拽排序、数据迁移、安装卸载及旧版更新回归。沙箱/合成图标先验证，真实桌面只读来源最后检查；不隐藏真实桌面来试验物理逻辑。

## 9. 实施阶段

1. **物理原型**：合成图标单窗口，完成碰撞、辅助线、球袋和回合状态；迁移上游行为测试并补边界测试。
2. **收纳来源及生命周期**：接当前分类/全部、启动入口、只读快照、同 EXE 游戏模式、IPC、本地设置/成绩，以及更新和退出联动。
3. **桌面镜像与体验**：只读桌面图标来源、品牌画面、入袋效果、暂停及多屏/DPI处理，不接入 Explorer 隐藏层。
4. **性能与发行**：完成资源回收、重复启停及数据不变测试，对照私有工作集和帧率；通过现有流程提交推送、构建、草稿哈希核验、发布和本机备份更新。

不预先将未来版本号写成已发布。只有达到可接受的运行开销、退出资源释放及数据保护要求，才进入安装版。

## 10. 后续单独评估

透明壁纸上的原版图层、全局排名、音效、皮肤和“入袋后执行真正收纳”均不纳入首版。这些会分别增加桌面恢复、服务、素材或文件操作边界，须另行设计。透明模式若采用隐藏 Explorer，需要持久恢复记录及独立异常恢复机制，不能用首版仅关闭游戏窗口的处理代替。

参考：[上游及审阅结论](图标台球接入分析.md)，原物理实现和许可均固定到已审阅的 eb8818f 提交。

## 11. 实施落地

首版采用 DesktopNook.Games.Core/BilliardsRound、Ball 与 Vec；界面通过 BilliardsSurface 自绘。IPC、三种来源、独立窗口、父进程成绩单写、维护前退出、异常断连、限额取图和 60 FPS 调度已接入；第三方 MIT 文本随单 EXE 嵌入。未创建长期日志和会话文件，按需保存两份游戏 JSON。

分类、收纳和排序不参加游戏状态写入；物理、原生界面、排序、游戏生命周期、存储及安装/旧版更新均有隔离检查。具体数量与性能数值记录在实现验收文档，不把本方案原定的初步目标当作已测结果。混合 DPI 多屏完整组合及透明 Explorer 图层仍不属于已验收结果。
