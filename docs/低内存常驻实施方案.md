# 轻匣低内存常驻实施方案

状态：已按任务管理器截图修订指标与实施优先级；当前安装版仍为 0.12.11。本文不代表下述目标已经实现。

## 1. 目标与选择

最新核验：任务管理器截图的 54.6 MB 与当前进程私有工作集 54.6 MiB 对应；同时总工作集约 134.6 MiB，专用提交约 175.4 MiB。它们是不同指标，不能把专用提交全部说成正在使用的物理内存，也不能把原方案的 60 MiB 专用提交目标与任务管理器的 54.6 MB 直接比较。见[微软对任务管理器内存列的说明](https://blogs.windows.com/msedgedev/2021/01/13/investigate-microsoft-edge-memory-usage/)。

**实施优先级修订：先在单进程内完成收起后的可重建资源释放、图标暂停和百叶有限缓冲复用，测量相同操作及闲置时间下的私有工作集。** 第一阶段目标为重复对照下私有工作集下降至少 20%（若基线仍约 54.6 MiB，则约 44 MiB 或更低），同时降低重复开合的提交峰值、不明显增加展开等待。这是待验证目标，不是收益承诺。总工作集和专用提交继续作为辅助指标，不通过裁剪工作集达标。

如果轻量改动收益不足，且需要进一步降低长期占用，再评估下面的进程分离方案。当前约 55 MB 的显示值不足以单独证明值得增加冷启动及双进程复杂度。

以下为第二阶段备选：**轻量入口常驻、界面按需运行、收起后延迟休眠**。长时间不用时只保留任务栏入口和唤醒能力；频繁使用时暂留界面进程，减少重新打开的等待。默认收起闲置 30 秒后让界面进程正常退出，再次点击任务栏时按原分类和滚动位置重新打开。

当前程序将入口、WPF 界面、图标提取和后台服务放在同一个进程，最小化后仍保留界面及运行环境。已有实测中，动画开启并反复使用后，收起 6 秒的专用提交为 165–183 MiB；关闭动画约 127 MiB。该数据来自合成图标并绕过任务栏发现，只作为基线参考。[分析与原始记录](运行时内存优化分析.md)保留了完整条件。

释放控件和缓存适合作为短期降耗，但不能保证进程内的框架、图形及系统组件全部退场。.NET 的程序集卸载需要可回收的 AssemblyLoadContext，并要求外部引用等条件满足，不能用清空窗口内容代替。因此，本方案使用进程边界管理重型界面的生命周期；这是基于当前结构和测量结果的工程选择，不将原生占用全部归因于 WPF。[微软程序集卸载说明](https://learn.microsoft.com/en-us/dotnet/standard/assembly/unloadability)

## 2. 用户感受到的行为

| 场景 | 处理方式 | 体验 |
| --- | --- | --- |
| 开机后台启动 | 只启动轻量常驻入口 | 有任务栏入口，暂不加载主面板 |
| 点击任务栏 | 唤醒或启动界面进程 | 恢复上次分类、位置及滚动状态，正常播放百叶展开 |
| 点击收起、Esc 或失焦 | 先播放收起动画，再最小化 | 保留现有 5 段、500 ms、从上到下收起 |
| 收起后 0–5 秒 | 保留近期界面状态 | 连续操作可快速重开，不反复重建 |
| 收起闲置 5 秒 | 释放可重建的图标图像、动画缓冲及已关闭弹窗引用 | 入口继续可用，停止无意义的界面工作 |
| 收起闲置 30 秒 | 保存界面会话状态，正常退出界面进程 | 进入低内存常驻，只留轻量入口 |
| 休眠后再次点击 | 启动界面并等待可绘制，再播放展开 | 首次重开会多一次加载，不能闪出空白面板 |
| 明确退出软件 | 退出入口和界面等所属进程 | 符合原“关闭时结束进程”设置 |

闲置从“收起动画完成且没有业务操作”开始计时。窗口仅被遮住、添加弹窗仍开着、菜单仍开着、正在拖拽、收纳、移回、保存、检查或下载更新时，不进入休眠。前台长时间不操作也不销毁界面。

设置提供“均衡（默认，30 秒休眠）”“优先响应（本次会话保留界面）”“省内存（5 秒休眠）”。初版先完成均衡模式，其他模式在相同生命周期控制器上实现；不新增每个页面各自的清理计时器。

## 3. 进程与兼容结构

```mermaid
flowchart LR
    T[任务栏点击 / 开机启动] --> H[轻量入口进程]
    H -->|启动或唤醒| U[WPF 界面进程]
    U -->|独占写入| D[现有数据与排序记录]
    U -->|收起闲置 30 秒，正常退出| H
    H -->|到期才启动| C[一次性更新检查]
    C -->|返回小型结果后退出| H
```

优先保持**一个发行 EXE、同一 EXE 的不同启动模式**：保留 DesktopNook.exe、程序集/Product 标识、AUMID、现有安装器和 GitHub 资产名。入口启动代码使用 Win32 消息窗口及最少量 .NET 服务；只有进入界面模式才初始化 WPF Application、资源字典和 Shell 图标工作线程。不能先创建 WPF Application 再判定进入后台模式。

这仍依赖现有 .NET 10 Windows Desktop Runtime x64。轻量入口不等于原生零运行时程序；其具体内存必须测量。原型验收要确认入口进程未因静态初始化、共享类或异常提示隐式加载 PresentationFramework、WPF 图形资源和 Shell 图标提取组件。

入口持有现有数据根目录对应的单实例身份、任务栏入口和唤醒事件。界面用内部启动模式运行，同一数据根目录最多一个界面实例。命名管道按当前用户限制访问，并用数据根目录签名、进程身份及会话随机值验证连接；只传唤醒、状态、退出请求等小消息，不传托管文件内容。

任务栏只有一个按钮。轻量入口负责其生命周期，界面不另建第二个按钮。按钮激活、最小化状态、缩略图、固定入口、应用分组及 Explorer 重启后的重建必须在原型阶段一起验证。**仅在主面板最小化时退出界面，不能用直接关闭全部窗口而丢掉入口代替。** 若上述任务栏行为不能保持，先解决宿主方案，再进入业务迁移；不将托盘图标替代任务栏入口作为默认退路。

## 4. 内存的具体处理

### 轻量常驻入口

只保存启动参数、少量会话状态、任务栏窗口与唤醒通道。分类索引、恢复清单、Shell COM 对象、图片、控件树和动画对象由界面持有。入口不持续扫描桌面、不轮询进程、不以逐帧回调判断闲置。

后台更新检查延续原有检查频率，改为到期后启动一次性检查模式，返回版本提示后退出；有界面时可由界面承接。检查任务全局最多一个，不为后台检查持续保留整个 WPF 界面。更新下载和安装必须沿用用户确认流程。

### 收起后的界面

动画一结束即移除时钟和临时绘制对象。暖驻留期间只允许一份有明确像素上限的可复用截图缓冲；闲置 5 秒后释放。图标缓存先以 2 MiB/64 项作为暖缓存实验预算，休眠前清空；像素预算不包含控件或图形系统副本，不能宣称是总图片占用上限。

必须同时清除控件 Source、缓存和异步交付引用。当前 ShellIcon 在最小化时不一定触发 Unloaded，故增加明确的暂停/恢复接口，暂停订阅布局及图标通知。图标请求使用会话代次，迟到结果不得重新挂回休眠视图；后台队列清除尚未开始且属于旧会话的任务，已开始的 Shell 调用允许安全完成后丢弃结果。

百叶动画同时做分配优化：对比一份缓冲复用与二维分段投影，保持 5 段、500 ms、展开下到上、收起上到下以及当前状态反向。选择必须以实际画面及内存/CPU 对照为准。二维实现和缓存预算是待验证参数，不是当前已实现的收益。

深度休眠靠界面进程退出释放其地址空间内的资源；不承诺驱动、系统文件缓存或其他进程的内存同步归零。默认不采用定期强制 GC 或裁剪工作集来达标。

## 5. 数据、退出与竞争处理

界面是收纳数据的唯一写入方，继续使用现有 NookStore 和原子保存，不新建另一套业务数据库。休眠不重排、不迁移、不复制或恢复用户内容。

收起保存当前分类 ID、滚动位置、键盘焦点和窗口状态；短时可由入口在内存中保留。重开时依据最新索引恢复：原分类已不存在则正常回退，不从会话状态覆盖成员、分类或 item-order.json。跨软件重启仍需保留的偏好写回现有偏好体系，继续保留关闭行为、默认添加视图、窗口尺寸及动画模式。

闲置控制器采用 `显示 → 收起中 → 暖驻留 → 释放缓存 → 请求休眠 → 已休眠 → 启动中` 状态及代次号。每次打开取消旧闲置请求；休眠退出请求与再次打开竞争时，入口保留最新目标，等待退出或取消退出确认后再唤醒，避免启动两个界面。

仅在拖拽、菜单、弹窗、存储和更新等活动租约均为零时，界面响应正常退出。入口须收到确认并观察到进程退出；超时先保留界面，不强杀正在写入的进程。休眠失败可保持当前暖驻留并记录小型诊断，不能影响下一次打开。

维护停止、覆盖安装和更新助手要同时停止入口及界面。**界面仍有操作或旧进程尚未退出时，入口不能提前释放原有互斥量、报告停止成功或允许替换 EXE。** 旧版助手到新版的首次升级、新版助手的就绪确认、异常回退、安装器路径及 PID 身份判断都需要专门回归。界面崩溃时入口保留，下一次唤醒重新加载现有恢复记录；不无上限自动重启。

## 6. 第二阶段备选的目标与验收

以下均为工程目标，尚未实测。先使用同一机器、相同隔离数据及完整任务栏路径验证，再补合成 URL 对照；图标数量至少覆盖 58、200、500 项。

| 指标 | 首轮目标 |
| --- | --- |
| 默认收起闲置 30 秒 | 界面已正常退出，除短时任务外只有入口驻留 |
| 收起 60 秒/5 分钟/30 分钟 | 全部所属存活进程的专用提交合计 ≤60 MiB，工作集合计 ≤80 MiB |
| 相同条件下相对原版 | 深度闲置专用提交降低至少 50% |
| 暖驻留重新打开 | 点击至首个可用画面 P95 ≤150 ms |
| 深度休眠重新打开 | 点击至首个可用画面 P95 ≤800 ms；500 ms 百叶时长另行记录 |
| 连续 100 次开合及多轮休眠唤醒 | 无孤儿界面、无多个写入方，末次深度闲置回到预算内 |
| 数据与行为 | 分类/排序/偏好保持，操作中不休眠，任务栏入口保持可用 |

监测同时记录专用提交、总工作集、私有工作集、托管堆、句柄、线程、CPU、打开耗时和后台任务时段。专用内存和工作集是不同指标；多进程总工作集可能重复计入共享页面，需披露这一点，不能只展示最小那个进程或只看任务管理器某一列。定义见[专用内存](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.privatememorysize64?view=net-10.0)及[工作集](https://learn.microsoft.com/en-us/dotnet/api/system.diagnostics.process.workingset64?view=net-10.0)。

P95 预热及冷启动分别至少采样 30 次；完整动画的首帧、完成时间和帧间隔单独记录。内存按开启前、展开、收起 5/30/60 秒、5/30 分钟采样，并连续记录峰值。后台更新任务独立标记其峰值和结束后的回落，不能回避该时段。冷启动目标失败则调整默认闲置时间或优化加载，不用空壳面板冒充可用画面。

## 7. 实施顺序与发布门槛

1. **结构原型。** 先实现独立入口与空界面的启动/退出、一个任务栏按钮及唤醒通道，确认同 EXE 多模式不会让入口隐式加载 WPF，并测量入口预算和冷启动。此阶段只用隔离目录。
2. **生命周期迁移。** 接入现有主面板和存储租约、会话状态、闲置计时、维护退出及异常处理。验证快速点击、休眠边界、弹窗/拖拽阻止休眠及多屏任务栏。
3. **压低暖驻留与峰值。** 接入图标暂停/恢复、有限缓存、过期任务丢弃和百叶缓冲优化。观察是否降低分配、是否增加冷启动或造成图标闪烁。
4. **完整对照及发行。** 重跑核心、原生界面、排序、动画、安装与旧版升级检查，完成 30 分钟驻留及多轮唤醒测量，达标后才提高版本号并按现有发布和同盘备份流程更新本机。

若轻量 .NET 入口仍超预算，先定位隐式加载或服务占用；仍不能达标时，再单独评估原生 Win32 入口的打包与更新成本。若只有进程内清理可交付，则如实公布较有限的实测降幅，不将其标成已经达到本方案的低内存常驻目标。
